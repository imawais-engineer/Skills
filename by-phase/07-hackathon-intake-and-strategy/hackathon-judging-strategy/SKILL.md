# Hackathon Judging Strategy

## Principle

Build for the judges without ignoring the users. Every major project choice should improve a judging criterion, reduce delivery risk, or clarify the demo story.

## Strategy Workflow

1. Convert judging criteria into score drivers.
2. Identify what evidence judges need to see for each score driver.
3. Define a project concept that makes those strengths visible in the demo.
4. Rank features by judging impact, requirement necessity, and build effort.
5. Identify differentiators that are feasible within the hackathon timebox.
6. Remove features that do not improve the rubric, demo, compliance, or core function.
7. Define success metrics and proof points for the pitch.

## Idea Scoring

Score each candidate idea against:

- Requirement fit
- Rubric fit
- Technical feasibility
- Demo clarity
- Use of required or sponsor resources
- Differentiation
- Security and reliability risk
- Submission complexity

Prefer the idea that can become a complete, working, judge-visible demo.

## Judging Evidence

For each criterion, define:

- Feature or workflow that demonstrates it
- Data, metric, screenshot, or live step that proves it
- Risk that could weaken the score
- Build task needed to make it visible

## Output

Produce a concise judging strategy:

- Recommended project direction
- Rubric-to-feature map
- Minimum winning demo
- Features to build now
- Features to defer
- Risks to manage

## Done Check

Judging strategy is done when the project has a clear path to score well and the demo can visibly prove the strongest criteria.
